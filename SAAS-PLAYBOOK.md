# SaaS-плейбук Pavel

> Живой документ-конвейер для запуска многих SaaS. Каждый новый продукт проходит по этим фазам;
> после каждого запуска секция «Журнал улучшений» дописывается — так плейбук самоулучшается.
>
> Владелец: Pavel (Минск, BY) · Бренд: **vibecode.by** · Основной инструмент: **Claude Code**
> Версия: v1 · Обновлено: 2026-06-08

---

## 0. Как пользоваться этим документом

1. Новая идея → копируешь чеклисты фаз 0–6 в отдельный файл проекта `C:\Projects\ClaudeCode\<saas>\PLAYBOOK-<saas>.md`.
2. Идёшь по фазам сверху вниз. **Не переходишь на следующую фазу, пока не выполнены exit-критерии текущей** — главная ошибка соло-фаундеров — строить MVP до валидации спроса.
3. После запуска (или убийства) проекта — дописываешь строку в [§10 Журнал улучшений](#10-журнал-улучшений-плейбука). Если урок системный — правишь сам плейбук.
4. Переиспользуемые ассеты (§8) живут в одном месте — `saas-starter/` — и копируются в каждый новый проект. Не настраивай auth/биллинг/email с нуля каждый раз.

**Принцип одной страницы:** на каждый проект — один файл-трекер, где видно фазу, метрики и go/no-go. Без этого «много SaaS» превращается в кашу.

## 1. Философия процесса

Три закона. Нарушение любого = слитые недели.

1. **Validation-first.** Сначала доказываешь, что за это платят, потом пишешь код. Дёшево проверить спрос (лендинг + вейтлист + 10–20 разговоров) стоит дни; написать ненужный MVP — недели. Правило: *no demand signal → no code*.
2. **Ship fast.** Цель MVP — **выходные–2 недели** на focused-работе (с Claude Code + boilerplate это реально: соло-девы шипят MVP за 1–2 недели против 2–3 месяцев раньше). Режь всё, что не нужно для первой оплаты.
3. **Расширяемость (compounding).** Каждый SaaS дешевле и быстрее предыдущего, потому что:
   - переиспользуемый стартер (auth/billing/email/analytics готовы);
   - этот плейбук пополняется уроками;
   - бренд vibecode.by растёт → каждый следующий запуск имеет аудиторию с нуля.

**Анти-паттерны (за что бьём себя по рукам):**
- Полировать продукт, который никто не ждёт.
- 30-дневный триал, бесконечный free-tier «чтобы понравилось» без пути к оплате.
- Менять стек на каждом проекте. Стек — фиксированный, кастомится только продуктовая часть.
- Запуск без канала дистрибуции (Product Hunt в вакууме = 0).

**Целевой профиль продукта для соло:** зарабатывает (люди реально платят) + просто повторить (узкий, не требует команды/саппорта 24/7) + узкая ниша (можешь стать №1 в маленьком сегменте, а не №50 в большом).

## 2. Фаза 0 — Поиск идеи

**Цель фазы:** 3–5 идей-кандидатов с гипотезой «кто платит и за что».
**Тайминг:** 1–3 дня. **Exit-критерий:** выбрана 1 идея с понятным платящим сегментом и существующими (платными!) конкурентами.

### Где брать идеи

| Источник | Как использовать |
|---|---|
| **TrustMRR** (`scripts/tools/trustmrr.mjs`) | Скан реальных MRR-данных indie-проектов. Ищем ниши, где уже платят, но продукты слабые/дорогие/узкие. Конкурент с MRR = доказанный спрос. |
| **Конкуренты** | Если у конкурента есть платящие юзеры и отзывы «не хватает X» / «дорого» / «сложно» — это вход. Лучше зайти в доказанный рынок «лучше/уже/дешевле», чем изобретать спрос. |
| **Боль рынка** | Reddit (`r/SaaS`, нишевые сабреддиты), отзывы в G2/Capterra (1–3 звезды = список фич, которых не хватает), запросы в X. |
| **Своя боль** | Автоматизации/боты, которые Pavel делает для себя (как этот personal-assistant) → продуктизация. Сильнейший сигнал — «я сам этим пользуюсь». |
| **vibecode.by** | Комментарии/DM под reels — аудитория сама подсказывает, что им нужно. |

### Критерии хорошей SaaS-идеи для соло (чеклист, нужно 4+/6)

- [ ] **Кто-то уже платит** за решение этой боли (есть конкурент с выручкой).
- [ ] **Узкая ниша** — можешь описать клиента одной фразой («фрилансеры-монтажёры, которым надо X»).
- [ ] **Низкий саппорт** — продукт не требует ручного онбординга каждого юзера / звонков.
- [ ] **Быстро повторить** — укладывается в стандартный стартер, без экзотики.
- [ ] **Есть канал** — знаешь, где живёт аудитория (сабреддит, X-комьюнити, твои reels).
- [ ] **Платёж проходит** — клиенты могут заплатить картой через MoR (см. §5). Не B2B-энтерпрайз с инвойсами/net-terms.

**Красные флаги:** рынок без денег («было бы круто, но платить не буду»), нужен сетевой эффект/двусторонний маркетплейс, тяжёлая регуляторика, конкурент — гигант с бесплатным аналогом.

## 3. Фаза 1 — Валидация ДО кода

**Цель:** доказать спрос, не написав ни строки продуктового кода.
**Тайминг:** ~1 неделя активной работы (бенч соло-фаундеров: ~30 дней на полную валидацию, но мы режем за счёт скорости лендинга и каналов).
**Exit-критерий (go/no-go):** см. ниже.

### Дёшево проверить спрос

1. **Лендинг + вейтлист.** Одностраничник: проблема → решение → одна кнопка «Get early access» (email). Собираем почты. Делается за пару часов из landing-шаблона (§8). Деплой на Vercel.
2. **Преданонс / посты.** Пост в целевом сабреддите / X / под reel: «делаю инструмент, который [боль]. Кому надо — оставьте почту / напишите». Смотрим реакцию.
3. **10–20 проблемных интервью / DM.** Не «понравится ли тебе фича», а «как ты решаешь это сейчас, сколько времени/денег тратишь, платил бы?». Вопросы про прошлое поведение, не про гипотетику.
4. **Fake-door / pre-order (по желанию).** Кнопка «Buy» ведёт на «скоро запуск, оставь почту/предзаказ». Клики на цену = сильнейший сигнал.

### Go / No-Go критерии

**GO (двигаемся в MVP), если хотя бы:**
- [ ] ≥ 20–50 email в вейтлисте за неделю с одного канала, **или**
- [ ] ≥ 5 человек сказали «да, заплатил бы» в интервью (конкретно, с ценой), **или**
- [ ] есть несколько кликов по «Buy»/предзаказу.

**NO-GO / пивот идеи, если:**
- Трафик есть, конверсия в почту ~0 → оффер/боль не цепляет.
- «Звучит круто» без действий → нет реальной боли.
- Никто не отвечает на DM/посты → нет доступа к каналу (нарушает критерий §2).

> Правило: лучше убить идею на этой фазе за неделю, чем на фазе MVP за месяц. No-Go — это успех плейбука, а не провал.

## 4. Фаза 2 — MVP

**Цель:** работающий продукт, за который можно взять деньги, с одной core-фичей.
**Тайминг-цель:** **выходные → максимум 2 недели.**
**Exit-критерий:** юзер может зарегиться → получить ценность → (в идеале) заплатить. Один happy-path работает end-to-end.

### Дефолтный стек Pavel (фиксированный — не пересматривается каждый проект)

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | **Next.js 15 (App Router) + TypeScript** | макс. AI-ассист, макс. доков, App Router — стандарт 2026 (RSC, server actions, streaming) |
| Хостинг/деплой | **Vercel** | уже в стеке Pavel, zero-config, превью-деплои |
| UI | **Tailwind + shadcn/ui** | быстро, копипастно, ИИ хорошо генерит |
| БД | **Neon (Postgres)** | уже в стеке Pavel, serverless, ветки БД под превью |
| ORM | **Drizzle** (или Prisma) | type-safe, лёгкий |
| Кэш/очереди/rate-limit | **Upstash (Redis)** | уже в стеке Pavel, serverless |
| Auth | **Better Auth** / NextAuth / Clerk | Better Auth — self-host, без vendor-lock; Clerk — если нужно «вчера» |
| Платежи | **Lemon Squeezy / Paddle / Polar (MoR)** | см. §5 — критично для BY |
| Email | **Resend** | транзакционка + react-email, дёшево |
| STT/AI | **Groq (Whisper)** + **Anthropic API** | уже в стеке Pavel; голос/ИИ-фичи |
| Боты/каналы | **Grammy (Telegram)** | конёк Pavel — TG-боты как продукт или как интерфейс к SaaS |
| Аналитика | **PostHog** (free tier) / Plausible | продуктовая аналитика + фичефлаги |
| Разработка | **Claude Code** | 95% кода; spec-driven: spec → plan → tasks → implement |

> **TG-ботный путь.** Сильная сторона Pavel — Telegram-боты (Grammy + Vercel + Upstash). Многие микро-SaaS можно отгрузить **как бота** с биллингом через Telegram Stars / MoR-чекаут по ссылке — без классического веб-дашборда. Это его конкурентное преимущество, отдельная продуктовая линия.

### Boilerplate-варианты (чтобы не писать стартер с нуля)

| Стартер | Цена | Когда брать |
|---|---|---|
| **ShipFast** (Marc Lou) | $199–349 one-time | классика «launch this weekend», Next + Stripe/Lemon Squeezy + Resend + auth. Опинионированный, под скорость. |
| **Supastarter** | платный | если нужна multi-tenancy/RBAC/i18n с первого дня (B2B). 5 платёжных провайдеров, Vercel AI SDK. |
| **T3 Stack** | free | type-safe full-stack, если хочешь собрать стартер сам и владеть кодом. |
| **Ixartz SaaS boilerplate** | free | бесплатная альтернатива платным: auth, multi-tenancy, roles, i18n, тесты. |
| **Свой `saas-starter/`** | — | **рекомендуемая цель** — см. §8. Один раз собрать (на базе одного из выше), дальше копировать. |

### Что включить в MVP / что отрезать

**Включить (load-bearing):**
- Auth (соц-логин + magic link).
- Одна core-фича (та, ради которой платят).
- Платёж + минимальный billing (1–2 плана).
- Landing с ценой.
- Базовый дашборд-скелет.

**Отрезать до запуска (добавишь, когда попросят платящие):**
- Команды/мультитенантность/RBAC (если не B2B-первого-дня).
- Настройки-богатство, темы, i18n.
- Свой биллинг-UI (берём customer portal от MoR).
- Админка, тяжёлая аналитика, онбординг-туры.

## 5. Фаза 3 — Монетизация и платежи (КРИТИЧНО для BY)

**Проблема:** **Stripe не работает для Беларуси** (санкции — RU/BY/UA не поддерживаются). Прямой Stripe на белорусское юрлицо невозможен. PayPal-приём тоже ограничен.

**Решение: Merchant of Record (MoR).** MoR — это юрлицо, которое продаёт твой продукт **от своего имени**: берёт деньги с клиента, платит налоги/VAT по всему миру, разбирается с чарджбэками, а тебе шлёт **payout**. Тебе НЕ нужно белорусское юрлицо с эквайрингом — нужен лишь способ получить выплату (счёт в поддерживаемой стране / Payoneer / Wise / Stripe Connect Express в стране выплаты).

> Это главный обходной путь проблемы белорусского юрлица. Без MoR — приём карт мира практически закрыт.

### Сравнение MoR (данные 2026)

| Провайдер | Базовая комиссия | Нюансы | Кому |
|---|---|---|---|
| **Paddle** | **5% + $0.50, all-in** | НЕТ доп. наценок за интернационал/подписки — для глобальной аудитории по факту **самый дешёвый**. Зрелый, B2B-friendly. | дефолт для SaaS с мировой аудиторией |
| **Lemon Squeezy** | 5% + $0.50, но интернационал-подписка ~**7% + $0.50** | простой, быстрый старт, любимец indie (часть ShipFast). Принадлежит Stripe. | быстрый старт, простые продукты |
| **Polar** | Starter **5% + $0.50** (с 2026, раньше 4%); старые 4%-экономику — только на платных планах ($20/$100/$400 в мес). Интернационал → эффективно ~6% + $0.40 | developer-native, GitHub-friendly. **Слаба** в proration/dunning/мультисит-подписках — для сложного B2B-биллинга не годится. | dev-tools, простой биллинг, OSS |
| **Dodo / Fungies** | сопоставимо | альтернативы, если основные не подойдут под нишу/страну выплаты. | бэкап-варианты |

**Дефолт Pavel:**
- **Paddle** — если аудитория международная и подписочная (по all-in-цене выходит дешевле всех).
- **Lemon Squeezy** — если нужно стартовать сегодня и продукт простой (one-time / простая подписка), особенно при использовании ShipFast.
- **Polar** — для dev-tools/OSS-монетизации с GitHub-аудиторией и простым биллингом.

> ⚠️ Перед выбором — проверить **страну payout** под Беларусь у конкретного MoR (поддержка выплат, Payoneer/Wise/банк в стране регистрации ИП/счёта). Это уточнение для Pavel (см. резюме).
>
> ⚠️ Telegram Stars — отдельный путь для ботов: приём прямо в TG без MoR (комиссия Telegram), затем конвертация. Удобно для микро-продуктов-ботов.

### Pricing-стратегия

Данные 2026:
- **Free trial конвертит лучше freemium** по сигнал-силе. Триал **с картой** → до ~30% trial→paid (5× против триала без карты). Freemium → обычно 2–5%, и до оплаты 90–180 дней против 12–18 дней у триала.
- **Длина триала 7–14 дней** с явным дедлайном бьёт 30-дневный на ~71%.
- Тренд 2026 — **гибрид**: freemium-вход + триал премиум-фич (65% PLG-продуктов).

**Дефолтная схема Pavel:**
1. Простой/вирусный продукт (ценность за <2 мин) → **freemium** с узким free-tier и явным апселлом.
2. Сложнее/выше чек → **7–14-дн триал с картой**.
3. Планы: держать 2–3 (например Free/Pro/`Team`), цены круглые, годовой план со скидкой.

### Подключение к стеку

- Вебхуки MoR (`subscription.created/updated/cancelled`, `order.paid`) → Next.js route handler → пишем статус в Neon.
- **Не катать свой billing-UI** — отдаём customer-portal/чекаут от MoR (управление подпиской, инвойсы, отмена).
- Фичефлаги/гейтинг по плану — через PostHog или поле в БД.

## 6. Фаза 4 — Запуск

**Цель:** первая волна юзеров и первые платящие.
**Exit-критерий:** продукт публично доступен, прошёл хотя бы один канал, есть первые регистрации/оплаты.

### Каналы

| Канал | Как |
|---|---|
| **vibecode.by (свой бренд) — канал №1** | Reels про процесс разработки этого SaaS = маркетинг. Build-in-public: «как я за выходные собрал X на Claude Code». Контент про процесс продаёт продукт **и** растит бренд одновременно. Это главное долгосрочное преимущество — каждый следующий запуск стартует не с нуля. |
| **Product Hunt** | Готовиться ~30 дней: maker-аккаунт 30+ дней, слот вт–чт, листинг-ассеты, прелонч-список саппортеров. Старт 12:01 PT, отвечать на каждый коммент весь день. Бенч топ-5: 300–500 апвоутов. **Видео в галерее 45–60 сек, работает без звука, вау-момент в первые 5 сек.** Цель: 200+ апвоутов и 30+ комментов в первые 6 ч. |
| **Reddit** | Нативные посты в целевых сабреддитах. Не реклама — история/польза («сделал инструмент для X, вот как»). Где живёт ниша. |
| **X / Twitter** | Build-in-public тред: процесс, цифры, фейлы, behind-the-scenes — сильнейшая тактика для indie. |
| **Директории** | На свежем моменте подать в BetaList, Launching Next, SaaSHub, smollaunch и пр. |
| **Telegram** | Свои TG-каналы/чаты, особенно если продукт — бот. |

### Чеклист запуска

- [ ] Landing с чётким оффером и ценой, мобайл-ок.
- [ ] Платёж протестирован end-to-end (тест-режим MoR → реальная оплата).
- [ ] Транзакционные письма (welcome, чек, сброс пароля) шлются (Resend).
- [ ] Аналитика стоит (PostHog: signup, activation, checkout-события).
- [ ] PH-ассеты готовы (видео, галерея, тэглайн, первый коммент мейкера).
- [ ] Прелонч-список (вейтлист из §3) предупреждён о дате.
- [ ] 2–3 reels про процесс сняты под vibecode.by.
- [ ] Посты в сабреддит/X написаны заранее.
- [ ] Мониторинг ошибок (Sentry/Vercel logs) включён.

## 7. Фаза 5 — Рост и поддержка

**Цель:** довести до устойчивого MRR или принять решение «убить/пивот».

### Метрики (минимальный набор)

| Метрика | Что значит | Ориентир 2026 |
|---|---|---|
| **MRR** | главный пульс. Разложить: New / Expansion / Churned / Contraction / Net | растёт = живём |
| **Activation rate** | % регистраций, дошедших до «ага-момента» (получили ценность) | низкая → проблема онбординга, а не маркетинга |
| **Trial→Paid** | конверсия триала | ~30% с картой — хорошо |
| **MRR Churn** | ранний сигнал бед раньше, чем падение MRR | B2B SaaS ~3.5%/мес (≈35%/год) — выше = течь |
| **NRR** | удержание+экспансия выручки | >100% = растём без новых юзеров |
| **CAC payback** | за сколько отбивается привлечение | <12 мес — здорово (для соло без paid-ads часто ~0) |

> Формула трезвости: *рост MRR − churn = реальный рост*. 10% роста при 8% churn = всего 2% — хрупко.

### Когда пивотить / убивать

**Убивать/пивотить, если после запуска + усилий по дистрибуции:**
- [ ] Activation на дне — юзеры регятся и не возвращаются (продукт не даёт ценности).
- [ ] Trial→paid ~0 несмотря на трафик (нет willingness to pay).
- [ ] Churn стабильно выше прироста (дырявое ведро — лить трафик бессмысленно).
- [ ] Нет органического канала — каждый юзер только за деньги/ручками.

**Растить, если:** есть платящее ядро, retention держится, есть хоть один работающий канал. Тогда — углублять core-фичу, поднимать activation, добавлять то, что просят **платящие** (не бесплатные).

> Решение «убить» — не провал. Освобождает время под следующий SaaS из конвейера. Урок → §10.

## 8. Переиспользуемые ассеты — «SaaS-стартер Pavel»

- [ ] Auth + платёж + landing с ценой.
