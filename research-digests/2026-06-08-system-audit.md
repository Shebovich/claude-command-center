## 2. Надёжность контура (poll-bot / heartbeat / reply)

**Архитектура:** `start-personal-session` спавнит два бесконечных Node-loop'а через Monitor: `heartbeat.mjs loop` (POST каждые 60s, TTL у бота 180s) и `poll-bot.mjs loop` (GET каждые 5s). Reply — разовый `reply.mjs`. Reminders — внешний cron-job.org (хорошо, не SPOF на этой машине).

### Единые точки отказа и поведение при сбоях

**Что хорошо:**
- poll-bot.loop **не падает на ошибке pull** — try/catch внутри while, логирует в stderr и продолжает (строки 110-116). Сетевой блип переживёт.
- heartbeat.loop так же устойчив к разовым фейлам, считает `fails`, печатает только смену состояния (умно — снижает риск self-injection, инцидент 02.06).
- Бот-side имеет TTL-fallback: если heartbeat не доходит >180s → бот сам отвечает Pavel «принято, отвечу позже» + догон при возврате. Это и есть страховка от смерти CC.

**Дыры:**
1. **Нет авто-рестарта процессов.** Если Node-процесс loop'а **упадёт целиком** (не словленное исключение, OOM, краш Node, закрытие Monitor) — он не перезапустится. heartbeat просто перестанет пинговать → бот переключится в echo-режим, но CC при этом «думает что работает». Никто не поднимает loop обратно автоматически. → **Нет watchdog'а.**
2. **Молчаливый poller.** poll-bot.loop при здоровье ничего не печатает; если он тихо умер, в CC-чате не появится сигнала. heartbeat печатает только FAIL/recovery. Итог: **оба loop'а могут умереть бесшумно**, и единственный индикатор — Pavel замечает echo-заглушки. Нет «liveness»-самопроверки что *оба* живы.
3. **Связка heartbeat-жив / poller-мёртв — худший случай:** heartbeat шлёт ok (бот думает CC онлайн, НЕ шлёт echo), а poller мёртв (сообщения не подхватываются). Pavel пишет → бот молчит без echo → сообщение висит в очереди необработанным. Это **тихая чёрная дыра**: бот считает себя живым, а ответов нет. Сейчас ничем не детектится.
4. **reply.mjs без ретраев.** POST notify разовый; если Vercel моргнул на этой секунде — ответ потерян, Pavel его не увидит, повтора нет.
5. **`_med-cache` растёт без TTL.** poll-bot качает каждое медиа в `_med-cache/<id>.ext`, никто не чистит (сейчас 8 МБ, не проблема, но монотонный рост).

### Рекомендации (без переусложнения)

- **R2.1 — Watchdog внутри heartbeat:** heartbeat уже единственный «всегда-должен-жить» процесс. Добавить в его loop проверку «когда последний раз poller что-то обработал» через общий heartbeat-файл (poller трогает `_tmp/poller.alive` mtime на каждом тике). Если mtime старше N сек → heartbeat шлёт боту флаг degraded (бот включает echo даже при живом heartbeat). Закрывает дыру #3 малой кровью. **(могу сделать сам)**
- **R2.2 — Bind: бот считает CC живым только если ОБА сигнала свежие.** Альтернатива R2.1 на bot-side: poller тоже шлёт лёгкий ping (или heartbeat несёт `poller_alive:true/false`). Эффект тот же, выбрать одно. **(требует правки bot-репо → ручной деплой Pavel)**
- **R2.3 — Ретрай в reply.mjs:** 2-3 попытки с backoff на сетевую ошибку/5xx. Дёшево, закрывает потерю ответа. **(могу сделать сам)**
- **R2.4 — Авто-рестарт loop'ов:** обернуть spawn в Monitor с until-петлёй или дать heartbeat-скрипту режим, который при детекте мёртвого poller'а сам его перезапускает. Минимально: документировать в skill, что Monitor должен ре388spawn'ить при exit. **(могу частично — скрипт; полноценный супервизор — обсудить)**
