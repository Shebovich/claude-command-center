## 1. Оркестрация субагентов / многоагентные системы

### 1.1 Субагент без чёткого ТЗ = дублирование работы
**Что:** Anthropic: каждому субагенту нужны 4 вещи — objective, output format, guidance по инструментам/источникам, и **clear task boundaries**. Короткие директивы вроде «research X» приводят к тому, что субагенты делают одинаковые поиски и оставляют дыры.
**Источник:** https://www.anthropic.com/engineering/multi-agent-research-system
**Как применить у нас (процесс ассистента):** когда делегирую через Agent tool — в промпт субагента всегда явно писать: (1) цель, (2) формат ответа (для меня — «верни ≤N строк сводку + пути к файлам»), (3) какие tools/источники использовать, (4) границы «не делай X, не трогай Y». Перестать слать односложные «изучи тему». Это ровно мой текущий разрыв — часть task'ов я формулирую слишком общо.

### 1.2 Effort scaling — масштаб субагентов по сложности
**Что:** Явное правило в промпте оркестратора: простой факт → 1 агент, 3-10 tool calls; сравнение → 2-4 субагента по 10-15 calls; сложный ресёрч → 10+ субагентов с разделёнными ролями. Без этого агенты либо недокапывают, либо жгут токены.
**Источник:** там же.
**Как применить (процесс):** до спавна прикидывать класс задачи и не плодить субагентов на тривиальном. Для self-improve циклов как этот — 1 агент с fan-out поиском (что и делаю), а не 5 параллельных на простую тему.

### 1.3 Токен-экономика: multi-agent = ~15× токенов чата
**Что:** агент ≈ 4× токенов чата; multi-agent ≈ 15×. Токены объясняют 80% разброса в качестве search-задач. Multi-agent оправдан ТОЛЬКО на: тяжёлая параллелизация, объём > одного контекста, много сложных инструментов. **Плохо для:** задач с общим контекстом и взаимозависимостями между агентами (напр. кодинг — мало параллелизуемых кусков).
**Источник:** там же.
**Как применить (процесс):** не делегировать ради делегирования. Кодовые правки dental-бота, где куски зависят друг от друга — делать сам в одном контексте, не дробить на субагентов. Делегировать ресёрч / независимый разбор логов / параллельные варианты дизайна.

### 1.4 Output offloading — субагент пишет в файл, не в контекст лида
**Что:** не гнать все выходы субагентов через лид-агента. «Artifact systems»: субагент создаёт персистентный output (файл), лид получает только указатель. Субагент жрёт 10k+ токенов, возвращает 1-2k сводку.
**Источник:** там же + https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
**Как применить (процесс):** это ровно мой паттерн с research-digests — субагент пишет полный .md, мне отдаёт ≤15 строк + путь. Закрепить как стандарт для всех тяжёлых делегаций (логи, ресёрч, генерация вариантов). Уже частично делаю — сделать дефолтом.

### 1.5 Чекпойнты вместо рестарта с нуля
**Что:** долгие агентные прогоны должны резюмиться с чекпойнта, а не с начала. Комбинировать адаптивность модели с детерминированными подстраховками (retry-логика). Перед переполнением контекста — сохранять план во внешнюю память, спавнить свежий субагент с чистым контекстом + аккуратный handoff.
**Источник:** multi-agent-research-system.
**Как применить (процесс):** для длинных автономных задач (idle-work режим) — писать промежуточный прогресс в memory/файл, чтобы при обрыве/переполнении продолжить, а не начинать заново.

## 2. Claude Code продвинутые приёмы

### 2.1 Субагент изолирует «грязный» контекст
**Что:** субагент полезен именно когда побочная задача завалила бы основной диалог результатами поиска/логами/содержимым файлов, которые больше не нужны. Он делает это в своём окне и возвращает только сводку. Свой system prompt, свой набор tools, отдельные permissions.
**Источник:** https://code.claude.com/docs/en/sub-agents
**Как применить (процесс):** для разбора больших логов dental-бота, чтения чужих кодовых баз, эксплорации — всегда субагент, не основной контекст. У меня уже есть специализированные агенты (.claude/agents/: lab-analyzer, hook-doctor, content-critic, scriptwriter) — это правильное направление, давать каждому узкий toolset.

### 2.2 PreToolUse hooks для детерминированных гардрейлов
**Что:** субагенты могут иметь lifecycle hooks. PreToolUse hook = условная валидация, когда поле `tools` слишком грубое (напр. разрешить Bash, но запретить конкретные опасные команды).
**Источник:** там же.
**Как применить (общее):** hook-doctor агент уже есть. Завести PreToolUse hook на dangerous bash (rm -rf, git push --force, запись вне разрешённых путей) — детерминированная страховка поверх вероятностной модели. Особенно для idle/автономного режима, где я работаю без подтверждений Pavel.

### 2.3 Context engineering — конкретные тактики
**Что (5 рычагов):**
- **Compaction:** при подходе к лимиту — суммаризировать историю, рестарт со сжатой сводкой + свежие файлы. Тюнить compaction-промпт: сперва recall (ничего не потерять), потом precision.
- **Note-taking / memory-файлы:** агент пишет заметки ВНЕ контекста (NOTES.md, to-do, тэли), подтягивает по нужде. Pokémon-агент держал точные счётчики тысячи шагов.
- **Just-in-time retrieval:** хранить лёгкие идентификаторы (пути, URL), грузить данные в рантайме, а не прелоадить всё. Эксплуатировать метаданные (иерархия папок, имена, таймстемпы).
- **Tool-result pruning:** старый сырой результат tool'а глубоко в истории — выбрасывать, сохраняя контекст решения. Самая безопасная лёгкая компакция.
**Источник:** https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
**Как применить (процесс):** моя MEMORY.md система = правильный паттерн (lightweight index + подгрузка по нужде). Усилить: (1) для длинных задач вести рабочий NOTES/прогресс-файл, (2) не прелоадить большие файлы целиком если нужен кусок — читать offset/limit (уже умею), (3) осознанно не таскать отработанные большие tool-выходы.

## 3. Надёжность Telegram-ботов на Grammy (dental-продукт)

> Стек dental: Grammy + node:sqlite + Gemini. Ниже — прод-практики из офиц. доков grammY.

### 3.1 Graceful shutdown — обязателен (иначе теряем/дублируем апдейты)
**Что:** ловить SIGINT/SIGTERM и звать `bot.stop()`. При остановке grammY делает финальный getUpdates с актуальным offset → синхронизирует позицию с Telegram, иначе при рестарте переобработка/потеря.
```js
// long polling
process.once("SIGINT", () => bot.stop());
process.once("SIGTERM", () => bot.stop());
// с runner:
const runner = run(bot);
const stop = () => runner.isRunning() && runner.stop();
process.once("SIGINT", stop);
process.once("SIGTERM", stop);
```
**Источник:** https://grammy.dev/advanced/reliability + https://grammy.dev/plugins/runner
**Как применить (dental-бот):** добавить signal handlers в entrypoint бота сразу. На хостингах с rolling-деплоем (Vercel/Railway/контейнеры) SIGTERM прилетает на каждый редеплой — без этого теряем сообщения пациентов на каждом апдейте кода.

### 3.2 Error boundaries + все промисы пойманы
**Что:** ВСЕ ожидаемые ошибки (API, сеть, БД, middleware) должны быть пойманы. Поставить lint-правило: каждый промис либо `await`, либо `.catch()`. Error boundary не зависит от polling/webhook. В long polling — обязательно ставить `bot.catch()`.
**Источник:** https://grammy.dev/guide/errors + reliability.
**Как применить (dental-бот):** глобальный `bot.catch(err => log + грейсфул-ответ пациенту «секунду, technical issue»)`, плюс try/catch вокруг Gemini-вызовов и node:sqlite запросов (особенно — таймаут на Gemini, чтобы зависший вызов не вешал апдейт). ESLint `no-floating-promises`.

### 3.3 Webhook vs polling для прода
**Что:**
- **Polling:** проще, не нужен домен/SSL/публичный URL. Но «скрытый контракт» — надо непрерывно звать getUpdates; замолчал надолго → Telegram дропает слот, сообщения копятся, на твоей стороне никто не замечает. Гарантия «at least once» (до 100 апдейтов могут переобработаться → дубли).
- **Webhook:** нужен публичный HTTPS. Дедупликацию exactly-once делать самому по `update_id`.
- **runner concurrent mode:** ни at-least-once, ни at-most-once — для критичных операций пускать апдейты через очередь.
**Источник:** https://grammy.dev/guide/deployment-types + reliability.
**Как применить (dental-бот):** для записи к стоматологу **webhook на serverless (Vercel)** логичнее — нет always-on процесса, который надо стеречь, и совпадает с SaaS-стеком плейбука. НО: реализовать дедуп по `update_id` (записи/слоты — критичны, дубль = двойная бронь). Хранить обработанные update_id в node:sqlite с TTL.

### 3.4 sequentialize — порядок сообщений в рамках чата
**Что:** при concurrent-обработке апдейты одного чата могут обработаться не по порядку. `sequentialize((ctx) => ctx.chat?.id.toString())` гарантирует порядок внутри чата при сохранении параллелизма между чатами. Константная память.
**Источник:** https://grammy.dev/plugins/runner
**Как применить (dental-бот):** если включаю concurrency — обязательно sequentialize по chat_id. Диалог записи (выбор услуги → врача → времени) ломается, если апдейты пациента переставятся местами. Для webhook-serverless с естественной обработкой по одному — менее критично, но при добавлении очереди вернуть.

### 3.5 Гочи runner (если пойду в concurrent polling)
**Что:** воркерам уходят только сырые updates — плагины из главного файла НЕ доходят, ставить плагины в файле воркера. Не спавнить больше тредов, чем физических ядер. Многопоточность оправдана только если >500 updates/sec (50M/день) — для dental-бота избыточно.
**Источник:** runner docs.
**Как применить (dental-бот):** НЕ городить многопоточный runner — объёмы стоматологии (десятки-сотни записей/день) этого не требуют. Webhook + простая последовательная обработка + дедуп. Сложность не нужна.

## 4. Дешёвая / локальная инференция (Ollama) — бюджет-философия

### 4.1 Гибрид: локаль для рутины, frontier для 10-15%
**Что:** прод-паттерн — локальная модель дефолт для high-frequency / low-stakes, cloud API только для ~10-15% запросов, которым реально нужен frontier. Локаль на потребительском железе = 70-85% качества frontier при нулевой марже за запрос.
**Источник:** https://dev.to/pooyagolchian/local-ai-in-2026-running-production-llms-on-your-own-hardware-with-ollama-54d0
**Как применить (общее / процесс ассистента):** у меня уже заложен Haiku для дешёвых классификаций. Альтернатива/дополнение — Ollama для совсем рутинного: классификация интента входящих TG, детект языка, короткие переформулировки, разметка «это трата / напоминалка / вопрос». Ноль стоимости, не жжём API-бюджет и не зависим от сети для тривиальщины.

### 4.2 Конкретные модели 2026 под рутину
**Что:** entry — 8B модель, 32K контекст, 12GB GPU: хватает на file ops, поиск, генерацию. Дефолты: `glm-4.7-flash` (лучший общий дефолт), `qwen3-coder:30b` (код), `qwen3.5:9b` (бюджет). Speculative decoding в llama.cpp даёт 1.5-2× скорости.
**Источник:** https://www.remoteopenclaw.com/blog/best-ollama-models-2026 + pooyagolchian
**Как применить (общее):** под рутину ассистента взять `qwen3.5:9b` или `glm-4.7-flash` через Ollama. ВАЖНО (фильтр под контекст): dental-бот юзает Gemini (free tier щедрый, мультиязык, vision) — НЕ менять на локаль; локаль = для МОЕЙ внутренней рутины и оффлайн-классификаций, не для пользовательских ответов пациентам, где нужно стабильное качество.

### 4.3 Точка окупаемости железа
**Что:** команды, обрабатывающие >10M токенов/мес, окупают железо vs API за 3-6 мес.
**Источник:** pooyagolchian.
**Как применить:** пока объёмы ассистента малы — Ollama не ради экономии денег, а ради (а) нулевой задержки на классификации, (б) приватности, (в) независимости от сети. Считать переход на локаль для прод-нагрузок только когда продукт даст реальный объём токенов.

## 🔧 К ВНЕДРЕНИЮ (топ-5, по польза/усилия)

1. **[dental-бот] Graceful shutdown + global bot.catch + дедуп по update_id.** (низкое усилие, высокая польза) SIGINT/SIGTERM→stop, глобальный error boundary, таймаут на Gemini-вызовы, дедуп update_id в node:sqlite. Без этого теряем/двоим записи пациентов на каждом редеплое и при сетевых сбоях. Сделать до любого паблик-запуска.

2. **[процесс ассистента] Стандарт делегации: полное ТЗ субагенту + output в файл.** (низкое усилие) В каждый Agent-промпт: objective / формат ответа / нужные tools / границы. Тяжёлый вывод — в .md, мне сводка ≤N строк + путь. Закрепить как дефолт (частично уже делаю) — убирает дублирование и экономит ~15× токенов на лишних multi-agent.

3. **[процесс ассистента] Не дробить взаимозависимое на субагентов.** (нулевое усилие, чистая дисциплина) Кодовые правки / задачи с общим контекстом — сам в одном окне. Multi-agent только на параллелизуемое (ресёрч, логи, варианты). Прямо из токен-экономики Anthropic.

4. **[общее] PreToolUse hook-гардрейл на опасные команды.** (среднее усилие) Детерминированная страховка (rm -rf, force-push, запись вне whitelist) поверх модели — критично для автономного idle-режима без подтверждений Pavel. У меня уже есть hook-doctor агент для этого.

5. **[общее] Ollama (qwen3.5:9b / glm-4.7-flash) для МОЕЙ внутренней рутины.** (среднее усилие) Классификация интента TG, детект языка, разметка трат/напоминалок — ноль стоимости, ноль сетевой задержки, приватность. НЕ трогать Gemini в dental-боте (там качество для пациентов важнее).
